# In plain words

This approach checks whether each old requirement's source and identifiable dependencies changed, then separately checks every new clause for distinct obligations. Clearly unchanged requirements receive an automatic unchanged decision; Claude reviews changed or uncertain cases in small batches. It reuses the repository's parsed text and matches clauses by paragraph labels and similar wording. The output keeps old IDs for changed or removed requirements and gives new obligations separate entries with citations. Its main weaknesses are missed implicit dependencies and differences in how the model splits obligations.

Repeated actions in a different test procedure or applicability context are kept as separate obligations. Claude receives parent sections to distinguish these from genuine renumbering; equal text at different citations is no longer deduplicated away.

# Technical

Deterministic alignment, candidate selection and exhaustive worklists use per-case JSON caches keyed by parsed inputs, requirements and relevant source bytes. Atomic writes protect interrupted preparation; progress messages distinguish recomputation from reuse. The prepared worklist is passed directly to execution, avoiding a second build. Model response caching and classification behavior are unchanged.

Case selection supports `dev` (R175 0.1.0 to 1.0.0) and `heldout` (R171 1.1.0 to 2.0.0). Held-out submissions, audits and logs are isolated in `outputs/heldout/`, with separate model caches and PDF-hash ingestion caches. Shared base ingestion is selected by configured regulation and checked against its version. Held-out configuration has not been run or scored.

1. Reuse the shared `data-ingestion/text/UN_R175_base.txt` and `data-ingestion/clauses/UN_R175_base.json`; process each new PDF once through `data-ingestion/pdf_to_txt.py` and `data-ingestion/txt_to_clauses.py`, cached by SHA-256.
2. Build an exhaustive Track A worklist for all supplied old requirements. Match their old source clause by paragraph/page, then attach same-label clauses, top lexical fuzzy matches, and clauses explicitly referenced by the requirement/source text.
   Recover sentence/list-item evidence across both documents using the requirement text, retaining two old and three new evidence blocks. Use new evidence scores in clause ranking, include named table/annex context, and generate exact word-level edits for the candidate obligation pairs. Require Claude to account for changed qualifiers and explain why any wording change is considered non-substantive.
3. Automatically mark an old requirement unchanged only when its unique same-label source, numbered parents and resolved dependencies match after whitespace normalization, its source page and parser boundaries are confirmed, and changed R175 section-2 definitions do not affect terms used in context. Resolve explicit paragraph/section/table/annex references recursively; changed, missing or uncertain references require model review. Batch remaining requirements in groups of ten. Combine local and Claude decisions with an exact-one-decision-per-ID check; emit only modified/removed results.
4. Build an exhaustive Track B worklist for every parsed new-version clause. Attach same-label old clauses and the top fuzzy matches from the old corpus, numbered parent context on both sides, and whether the paragraph number existed before. Require scope continuity evidence and an old clause ID before treating a newly numbered provision as existing or modified-existing. Repeated actions in separately introduced procedures remain new; uncertain equivalence is retained with an explanation.
5. Batch Track B in groups of six. Claude inventories independently executable steps, testable operating cases, and distinct actions/permissions in an internal coverage list, then extracts and classifies each as existing, modified-existing, or genuinely new. Conditions and alternative ways to satisfy one obligation remain attached. Validate a one-to-one mapping from included units to output entries and reasons for exclusions; correction retries handle invalid mappings. Emit only genuinely new obligations. This cannot prove completeness of the model's inventory and has not yet been benchmarked.
6. Cache each structured response by model, prompt, and schema hash. Retry recoverable failures up to three application-level attempts; stop immediately on permanent HTTP 4xx errors such as 400. Log usage and estimated cost. Save full alignment and decisions for miss diagnosis.
7. Send an API-compatible structural schema to Claude, retaining numerical and string limits in local validation. Validate exact worklist coverage, source page/paragraph against parsed clauses, requirement IDs, output schema, and submission fields before writing `outputs/subgoal-<case>.json`. Deduplicate additions only when normalized text and paragraph/page citation are equal. Scope-aware matching has not yet been run or benchmarked.
8. The local benchmark reports precision/recall by change category and uses a citation-plus-text threshold only as a proxy for matching added obligations; the platform score remains authoritative.
   Supported list-item citations are normalized to the parsed parent paragraph after checking the page and item marker; the audit preserves the original citation. `--assemble-only` assembles a complete, unambiguous cached review set without API calls, including runs made with the previous batch size.
9. Alignment uses lexical similarity, not embeddings. Old obligations are compared through retrieved clause text rather than a separate atomic extraction pass. The automatic shortcut traverses resolved dependencies but cannot guarantee discovery of implicit applicability changes; Claude receives at most five referenced clauses per version. The current shortcut has not been run or scored. Development-driven architecture changes and the single labelled case are declared in `risk.json`.
